AI Product Analysis

Overall Conclusion

在本次多文档、多针检索与推理评测中，ToolAugmentedAgent 在三轮重复运行下取得了 7.3 分的平均分，其中 72.7% 的运行达到“Good”水平，整体表现中等偏上，但距高可靠自动化仍存在明显差距。按任务类型看，date_time 几乎无短板（均分 9.2，仅 6 个坏例），而 computation（均分 6.67）、string_analysis（6.27）和 encoding（7.07）则暴露出系统性的不稳定：同一案例在三轮运行中出现 0 分与 10 分并存的现象较为常见，说明当前管线在关键证据获取和操作计划执行上存在随机性失败。工具诊断进一步揭示，37 次“tool_augmented_failed”中，因“缺失必需证据”回退高达 20 次，是首要失败模式；“不支持的操作”9 次、“操作解析失败”5 次与“解码输出无效”3 次共同构成了能力边界。综上，Agent 在简单日期推理上已具备生产级能力，但在需要精准检索多处分散证据并组合计算的场景中，检索完整性与计划可靠性已成为制约整体表现的瓶颈。

Main Capability Gaps

工具路径统计显示，20 次 fallback 源于“missing_required_evidence”，出现频次远超其他失败原因。在多 needle 环境下（平均深度 46.4），Agent 经常无法同时召回所有必需的数字、令牌或编码线索，直接导致后续计算或分析使用错误或缺失的输入值。典型如案例 1128（string_analysis），三轮中两轮得 0 分，应答字符计数与真值偏差极大，极有可能是未检索到正确的令牌字符串而误用了无关文本块。

  • 跨文档多针检索覆盖不全

尽管工具集已包含确定性的 Python 执行能力，computation 和 string_analysis 任务均分仍不足 7 分。案例 615 中，所有三次运行均给出荒谬的大整数结果，显然操作计划未正确映射“减法”逻辑，或错误组合了多个大数，而非执行失败。另有 5 次“invalid_operation_parse”回退，说明 LLM 生成的计划在结构化解析阶段即被丢弃，制约了一次重规划路径的有效性。

  • 操作计划质量波动与解析脆弱性

encoding 任务均分仅 7.07，且出现“invalid_decoded_output”3 次。坏例 1518 在三轮中以“Unknown”或错误值“TWLS451”结束，提示当前解码工具链既无法处理某些特定编码方法（unsupported_operation），也可能在成功执行时输出错误结果。这限制了 Agent 在情报类场景中的实用价值。

  • 编码解码工具覆盖不足与解码正确性

Bad Case Attribution

依据工具诊断将坏例归结为以下可追踪原因：

  • 证据缺失主导（missing_required_evidence 20 次）：多数计算与字符串分析的零分线路，根因在于混合检索未能召回全部相关 needle。例如案例 1128 在三次运行中的两次应答分别为“0”和“12”，而真值为 8，说明所操作的字符串对象已不是题面指定的令牌；案例 430（computation）三轮全 0 分，推测至少一个关键数值块未被检索到。
  • 操作计划错误：案例 615 对所有三轮给出远超出数值范围的答案，逻辑上属于计划层将减法误构为乘法或拼接。案例 658 三次中仅一次正确，两次给出错误的大整数，印证 LLM 在映射字段和组合操作时存在随机失误，而非 Python 执行器出错。工具诊断中“invalid_operation_parse”5 次、“unsupported_operation”9 次也表明计划生成质量不稳定，部分计划无法被正常解析或调用了不存在的工具能力。
  • 解码输出错误或不完整：encoding 类的 0 分运行（如 1518、1359、1276）多以“Unknown”或错误字符串返回。“invalid_decoded_output”3 次直指解码函数在部分输入上生成了与真值不符的字符串，可能是内置映射表不全或编码参数推断错误；而“unsupported_operation”9 次中有相当比例可能出现在编码解码任务，导致 Agent 无法调用合适的解码原语而直接兜底输出。
  • 答案格式归因轻微：仅 1 个案例出现“Partial”结果，表明多数失败并非答案归一化问题，而是推理或工具链产出错误值；深度在此环境中仅为辅助指标，未观察到与深度线性相关的失败模式。

Actionable Optimization Suggestions

结合该 Agent 的规划器‑工具架构和诊断数据，建议按以下方向迭代，不引入个案硬编码：

  • 增强多针检索覆盖与证据校验
  • 在混合检索后引入更严谨的必要性检查：LLM 在生成操作计划前，必须列出所需的所有证据项及其预期来源，若某项缺失则触发扩大召回（增加邻居块数、降低重排序阈值或补充关键词扩展）。
  • 实现轻量级证据冲突检测：当检索到多个候选令牌/数值时，通过交叉验证或置信度评分筛除低质量块，减少误用无关文本的概率。
  • 提升操作计划的鲁棒性与可解析性
  • 使用结构化计划模板强制 LLM 以“字段→操作→预期输出类型”格式输出，并在解析前进行 schema 校验，减少“invalid_operation_parse”。
  • 对于 computation 与 string_analysis，在计划中嵌入合理性约束（如计算结果范围、字符计数非负等），一旦 Python 执行结果突破约束则触发一次自动重规划。
  • 完善编解码工具矩阵与自校验
  • 通过工具诊断识别当前覆盖缺失的编码方法（如某些置换或自定义 base 变种），实现一组可组合的通用编解码基元（如：移位、置换、base 转换），让 LLM 通过参数组合实现新编码，降低 unsupported_operation 频率。
  • 对解码输出增加格式校验（期望字符串模式、长度或前缀），若输出为“Unknown”或与格式不匹配，则尝试备用解码路径或上报给 LLM 二次决策。

现有重规划已部分启用，但在缺失证据或计划解析失败时，应显式携带失败原因返回给 LLM，让重规划能够针对性调整（如显式要求检索到具体标识符的块，或更换操作名）。避免无提示的盲重试，提升从 0 分到成功的恢复率。

  • 强化一次重规划机制的有效性
