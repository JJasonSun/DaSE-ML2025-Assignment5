AI Product Analysis

Overall Conclusion

本次评测对 HybridRetrievalAgent 在 100 个多文档、多针检索与推理用例上执行了 300 次运行，整体平均得分仅为 2.06（满分 10），失败运行高达 237 次（Fail），仅取得 49 次 Good 和 14 次 Partial。从任务类型看，computation（均分 0.6）和 string_analysis（均分 0.31）几乎完全失效，encoding（均分 3.15）和 date_time（均分 4.17）表现稍好但同样不稳定，过半运行仍为失败。总体而言，该基线虽然通过混合检索提供了上下文，但后检索阶段的推理与格式输出能力严重不足，无法满足多文档、多针刺场景对精确计算、编码解码和字符串分析的要求。

Main Capability Gaps

computation 与 string_analysis 两类任务得分极低，绝大多数回答错误或返回“Unknown”。即使在检索到正确数据的情况下，LLM 仍无法完成整数平方根、大数乘积、MD5 哈希等操作，暴露出其在无外部工具辅助时缺乏可靠的计算与字符串处理能力。

  • 后检索精确推理严重缺失

encoding 类案例多次出现直接返回 Base64 编码串而非解码结果（如输出 UEhPRU5JWDY0NQ== 或原样回传 payload ID），说明模型没有按照检索到的协议说明执行解码步骤，推理链路断裂，未能将上下文知识转化为正确的产出。

  • 编码解码过程不规范

虽然 date_time 类问题出现一些满分案例，但 bad_cases 仍高达 44/75 次运行。部分失败与日期漂移、工作日计算或时间间隔推算的逻辑错误有关，而非完全检索不到信息。

  • 日期时间推理不够稳定

工具诊断显示所有运行仅依赖 hybrid_retrieval，无任何 fallback 路径或验证步骤。一旦 LLM 推理出错，系统既无法自纠也无法降级处理，导致失败直接暴露为最终答案。

  • 缺乏推理失败检测与纠偏机制

该回答的直接原因是 LLM 意识到自身无法计算 MD5 哈希，从而放弃输出。即使参与检索的 chunks 包含正确的加密密钥字符串，后检索的模型能力短板依然导致失败，属于典型的 post-retrieval reasoning 限制。

  • string_analysis 类哈希计算（如 case 1104，回答 “Unknown”）

检索到的上下文很可能覆盖了编码文本与协议说明，但 LLM 在回答时跳过了“解码”这一关键动作，直接输出编码本身。这表明当前提示策略未能充分强制模型进行解码操作，或相关协议描述在检索片段中被截断、未形成清晰指令，是检索后推理与提示引导不足共同作用的结果。

  • encoding 类解码错误（case 1397 返回 Base64 值，case 1454 返回原始 payload ID）

模型能定位到运算所需的源数值，但最终生成数字时并未严格计算，而是依赖语言模型自身的生成分布近似“猜”出结果，导致精度与一致性不可接受。这定性为典型的纯 LLM 推理失败，而非检索遗漏。

  • computation 类数值偏差（case 655 输出接近正确，case 568 结果完全错误）

平均针深度为 45.63，部分信息位于文档深处，但从 date_time 和 encoding 任务的部分成功可以看到，检索并非全局瘫痪。现有 bad case 更强烈地指向 post-retrieval 推理缺陷，深度因素是否恶化检索质量尚缺详细 trace 佐证，暂不作为主要归因。

  • 深度因素影响有限

Actionable Optimization Suggestions

不加装计算器、解码器等外部工具，仅从检索优化与 LLM 分步推理引导角度提出以下建议：

在最终回答提示中明确要求：“先列出检索到的关键数值/编码文本”、“写出中间运算或解码步骤”、“再给出最终答案”。这有助于将隐式推理转为显式工作记忆，降低跳步或直接预测的风险。

  • 强化多步推理提示结构

检查 selected_queries 是否覆盖运算所需的全部标识符与协议关键词，可对包含 “protocol”、“decode”、“encoding”、“MD5”、“hash” 等术语的片段进行针对性扩展，确保检索召回完整的规则描述块，而非仅返回孤立的数值。

  • 优化查询扩展策略

利用 rerank_scores 保留高相关片段，并通过 neighbor_radius 适当拉取编码协议或计算步骤周围的上下文，避免因 chunk 切割丢失操作说明。对于深层信息可考虑放宽邻居半径，提升完整证据被送入 LLM 的概率。

  • 调整重排序与邻居块扩展

在提示中要求模型进行自检，例如“请反算验证结果是否一致”或“确认解码后的文本不含非打印字符”。同时明确禁止输出 “Unknown” 这类放弃信号，对数字型答案强制要求纯数字格式，对解码类答案指明仅输出可读字符串。

  • 引入自检与格式约束

当可完整获取 selected_queries、retrieved_files、rerank_scores 等字段后，可进一步区分是哪一环节导致失败：若关键段落未被召回，则调整 BM25/密集嵌入权重；若段落已召回但模型仍处理错误，则集中力量打磨推理提示与 self-check 机制。

  • 利用检索 trace 进行复盘诊断

以上建议均围绕现有 hybrid retrieval 管线展开，不引入确定性工具，有助于在保持检索基线定位的前提下，系统性地减少后推理失败，提升多文档、多针聚合场景下的整体作答质量。
